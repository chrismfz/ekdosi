## 2. Τι υπάρχει ήδη: SoftOne (τιμολόγηση) + HeartbeatOS (αγνοείται για αρχή)

### 2.1 Ποιος κόβει σήμερα τα παραστατικά (από το myDATA, μέσω του HBOS)
Το HBOS **διαβάζει** το myDATA του πελάτη (`RequestTransmittedDocs`/`RequestDocs`,
1.891 έγγραφα από 2026-07). Οι σειρές εσόδων αποκαλύπτουν τη ροή:

| Σειρά | Τύπος | Ιούλ | Αύγ | Σεπ | Ερμηνεία |
|---|---|---|---|---|---|
| **ΛΙΑΣ** | 11.1 ΑΛΠ | 559 | 254 | 233 | **e-shop** — ταιριάζει 1:1 με τις ολοκληρωμένες παραγγελίες (Αύγ 268, Σεπ 229+3) |
| **ΛΙΑΚ** | 11.1 ΑΛΠ | 188 | 172 | 130 | **φυσικό κατάστημα** |
| **ΕΛΠΣ** | 11.4 πιστωτικό λιανικής | 97 | 52 | 26 | επιστροφές e-shop (**~10–20% των ΑΛΠ**!) |
| ΤΔΑ/ΧΤΔΑ, ΠΤΔ, ΠΕΚ | 1.1 / 5.x | λίγα | | | χονδρική/B2B (σπάνια) |

- Τα ΑΛΠ του e-shop κόβονται **ήδη 1:1**, από το **SoftOne** (δεν υπάρχει
  plugin τιμολόγησης στο WP, και ο αριθμός ΑΛΠ **δεν** γράφεται πίσω στην παραγγελία —
  0 order notes/meta). Πιθανότατα πληκτρολογούνται/εισάγονται χειροκίνητα ~250/μήνα +
  ~50 πιστωτικά. **Αυτό είναι ο πόνος που λύνει το ekdosi.**
- Άρα το ekdosi **αντικαθιστά το SoftOne ολόκληρο**: σειρά e-shop (ΛΙΑΣ/ΕΛΠΣ) μέσω της
  Woo γέφυρας **και** σειρά καταστήματος (ΛΙΑΚ) μέσω του POS (§11). Νέα σειρά ή συνέχεια
  αρίθμησης → §10.5.
- Το HBOS θα «βλέπει» αυτόματα τα ΑΛΠ του ekdosi μέσα από το δικό του myDATA read —
  **καμία ενσωμάτωση δεν χρειάζεται για αυτό**.

### 2.2 Το HeartbeatOS (HBOS)
Laravel SaaS «Ecommerce Operating System» (εξωτερικός developer). Live σήμερα:
παραγγελίες (mirror από Woo), αποστολές/vouchers (3.473), tracking (414k events),
**απόδοση αντικαταβολών** (`courier_settlements` 57 / `courier_settlement_rows` 553),
customer care/επιστροφές (`customer_cases` 464, `case_refunds` 18), Finance Engine
(ledger, myDATA **read-only** — `MyDataConnector::fetchDocuments`, χωρίς αποστολή).

**Roadmap του HBOS (σημαντικό):** `HB-005 Inventory Foundation`, `HB-012 WMS`,
`HB-013 ERP`. Ήδη: `wms_skus` 7.711 γραμμές συγχρονισμένες **read-only** από το Woo ανά
παραλλαγή (`WmsVariationSyncService`), αλλά `wms_stock`/`wms_movements`/`warehouses` = **0**
(το WMS δεν είναι live). **Το HBOS σκοπεύει να γίνει και πηγή στοκ** → σύγκρουση
ιδιοκτησίας αν το ekdosi γίνει κι αυτό πηγή στοκ (§3, §9.1).

**WP plugins του HBOS:** `heartbeat-os-connector` (mirror events + `heartbeat/v1/sync/*`)
και inbound `order/set-voucher` (γράφει `_courier_voucher`/`_courier_company`, και με
`complete=true` → status **`completed`**), `order/complete-pickup` (`_hbos_store_pickup=1`
+ completed), `order/unset-voucher` (πίσω σε `processing`). `hbos-order-portal` = κουμπί
self-service στα emails. Το παλιό `vp_shipments_ledger` είναι **νεκρό** (όλα `unknown`).

## 3. Ποιος είναι ιδιοκτήτης κάθε δεδομένου

**Κανόνας: κάθε πεδίο έχει ΕΝΑΝ ιδιοκτήτη.** Two-way sync στο ίδιο πεδίο = σίγουρο overwrite.

| Δεδομένο | Ιδιοκτήτης | Ροή |
|---|---|---|
| Παραγγελίες | Woo | Woo → ekdosi (Εισερχόμενα) |
| **ΑΛΠ/πιστωτικά, ΑΑ, MARK, PDF** | **ekdosi** | ekdosi → myDATA· → Woo (order meta/note + PDF στον πελάτη) |
| Voucher, tracking, COD settlement, επιστροφές | HBOS | HBOS → ekdosi (προαιρετικό, Φάση 5) |
| **Κατάλογος + στοκ + barcodes** | **ekdosi** (δρόμος Α) | ekdosi → Woo |
| SEO, περιγραφές, κατηγορίες shop, swatches | Woo | — |

**Στοκ — ΑΠΟΦΑΣΗ: δρόμος (Α).** Με το SoftOne να φεύγει και το κατάστημα να κόβει από
το ekdosi POS, το ekdosi είναι η μόνη θέση που βλέπει **όλες** τις πωλήσεις → πηγή
καταλόγου/στοκ/barcodes. (Το HBOS αγνοείται· αν αργότερα θέλει στοκ, **διαβάζει** από ekdosi.)
Οι δύο δρόμοι, για το ιστορικό της απόφασης:
- **(Α) ekdosi = πηγή στοκ/καταλόγου** (το αρχικό αίτημα: φωτογραφίες, νούμερα,
  χρώματα στο ekdosi → Woo). Δουλεύει **μόνο αν** και το κατάστημα (ΛΙΑΚ) κόβει από το
  ekdosi και το HBOS **δεν** γίνει κι αυτό πηγή στοκ (το HBOS WMS τότε διαβάζει από ekdosi).
- **(Β) ekdosi = μόνο παραστατικά**· στοκ στο Woo σήμερα / στο HBOS WMS αύριο. Το ekdosi
  γράφει μόνο κινήσεις όταν τις ζητήσει κάποιος. Λιγότερη δουλειά, μηδέν σύγκρουση.
- Η γέφυρα παραγγελιών → ΑΛΠ (Φάσεις 1–2) είναι **ίδια και στους δύο** → ξεκινά ανεξάρτητα.

## 4. Πότε κόβεται το ΑΛΠ — ένα σημείο ενεργοποίησης

**Trigger (γενικό, universal):** ρυθμιζόμενο status ανά σύνδεση — default
`completed`. **Για αυτόν τον πελάτη** `completed` = «βγήκε voucher» (το HBOS το θέτει)
ή παραλαβή από κατάστημα, **όχι** «παραδόθηκε».

| Ροή | Πότε | Πώς |
|---|---|---|
| Viva / Πειραιώς / PayPal | στο `completed` | auto ΑΛΠ, **εξοφλημένο** (payment με `transaction_id`) |
| Κατάθεση (`bacs`) | στο `completed` (έχει ήδη επιβεβαιωθεί) | auto ΑΛΠ, εξοφλημένο |
| **Αντικαταβολή** | στο `completed` (= αποστολή) **ή** στην παράδοση — **§10.1** | auto ΑΛΠ, **ανοιχτό υπόλοιπο** |
| Απόδοση COD | courier settlement (HBOS ή αρχείο courier) | μαζικές πληρωμές → κλείνουν υπόλοιπα (Φάση 5) |
| Παραλαβή από κατάστημα | `completed` + `_hbos_store_pickup` | auto ΑΛΠ (ίδια σειρά e-shop) — **εκτός** αν πληρώνεται/τιμολογείται στο ταμείο (§9.3) |
| Επιστροφή / άρνηση | γεγονός επιστροφής | **πρόταση πιστωτικού (11.4)** στο inbox, χειροκίνητα (`IssueCreditNote`) — ~50/μήνα σήμερα |
| `cancelled` / `failed` | — | ποτέ |

**Idempotency = `(billing_connection_id, order_id)`, ΟΧΙ voucher.** `unset-voucher` →
νέο voucher **δεν** κόβει δεύτερο ΑΛΠ. ΑΛΠ ήδη κομμένο + παραγγελία → `cancelled`
→ πρόταση πιστωτικού.

**Inbox μόνο για εξαιρέσεις:** σύνολο ΑΛΠ ≠ σύνολο παραγγελίας (έστω 0,01), χώρα
εκτός GR, άγνωστο fee/payment method, (μετά τη Φάση 3) παραλλαγή χωρίς αντιστοίχιση.
Με ~250/μήνα το inbox θέλει **μαζική έκδοση**.

## 5. Αντιστοίχιση παραγγελίας → γραμμές ΑΛΠ

**Ποσά:** το Woo **δεν** υπολογίζει ΦΠΑ (`calc_taxes=no`), άρα `line.total` = μικτό.
Το ekdosi: καθαρό = μικτό / 1,24 (ανά κατηγορία ΦΠΑ του προϊόντος· αρώματα/ρούχα = 24%),
στρογγυλοποίηση μόνο στην ανάθεση (CLAUDE.md math). **Το σύνολο του ΑΛΠ πρέπει να βγαίνει
στο λεπτό ίδιο με το `order.total`** — αλλιώς εξαίρεση στο inbox, ποτέ σιωπηλή διόρθωση.

| Order item | n (ιστορικό) | Χειρισμός |
|---|---|---|
| shipping «Δωρεάν μεταφορικά» | 3.593 | 0€ → **παραλείπεται** |
| fee «Χρέωση αντικαταβολής» | 2.833 | γραμμή υπηρεσίας (ΦΠΑ: §10.3) |
| coupon `card10` (το −10% online) | 1.131 | ήδη μοιρασμένο στα `line.total` → **έκπτωση γραμμής %** = (subtotal − total)/subtotal |
| shipping BOX NOW lockers / Delivery | 723 | γραμμή μεταφορικών όταν > 0 |
| fee «Χρέωση τρόπου πληρωμής» | 104 | γραμμή υπηρεσίας |
| shipping «Παραλαβή από το κατάστημα» | 71 | 0€ → παραλείπεται |
| fee «Extra Winter Discount (−20/−30%)» | 27 | **αρνητικό fee** → όχι αρνητική γραμμή· **έκπτωση παραστατικού %** (`DISCOUNT_inv`) |

- **Πελάτης λιανικής:** ΑΛΠ χωρίς counterpart (κανόνας retail, `docs/mydata-submit-payload.md`).
  Customer record ανά email για ιστορικό/portal — προαιρετικό.
- **Τρόπος πληρωμής myDATA** (πρόταση → §10.2): Viva/Πειραιώς → 7 (POS/e-POS) · PayPal → 6 ·
  `bacs` → 1 · IRIS → 8 · `cod` → **;** · κατάστημα → 3 ή 7.
- **Γενικό (universal):** mapping `payment_method` → myDATA code, fee/shipping name → είδος
  γραμμής, trigger status — όλα **ρυθμίσεις ανά σύνδεση**, όχι hardcoded για αυτόν τον πελάτη.

## 6. Φάσεις

**Φάση 1 — Γενική Woo γέφυρα + inbox (παραγγελίες → ΑΛΠ).**
Phase 1 του `bridges-connectors.md §9`: `BillingSource` data methods από **δύο** σχήματα
(WHMCS invoice + Woo order), `billing_connections.config` (`base_url`, `consumer_key/secret`,
`webhook_secret`, mappings §5), νέος tenant. Woo webhooks `order.created/updated` + REST
poll ως δίχτυ. Γραμμές με `woo_product_id`/`woo_variation_id` + περιγραφή «Όνομα — Χρώμα /
Μέγεθος». Write-back ΑΑ + MARK + PDF link σε order meta/note. Χειροκίνητη + μαζική έκδοση.
**Μόνο του αυτό αντικαθιστά την πληκτρολόγηση ~250 ΑΛΠ/μήνα.**

**Φάση 2 — Αυτόματη έκδοση** με τους κανόνες του §4 (ανά payment method, default OFF) +
πιστωτικά 11.4 από το inbox.

**Φάση 3 — Παραλλαγές στο ekdosi + import καταλόγου** *(προαπαιτούμενο και του POS, §11)*.
- `products.parent_product_id` + `variant_attributes` (json). Παραλλαγή = **κανονικό
  Product** → στοκ/κινήσεις/reorder (`StockService`, `stock_movements`) όπως είναι.
  **Όχι** ξεχωριστός πίνακας `product_variants`.
- Δομή shop: **κάθε** παραλλαγή = χρώμα (`pa_1001`, 3.664/3.664) × μέγεθος από **μία
  κλίμακα ανά κατηγορία**: `pa_1004` γενικά (2.556), `pa_1003` παντελόνια (641),
  `pa_1002` ανδρ. παπούτσια (293), `pa_1005` κοστούμια (114), `pa_1006` σακάκια (44),
  `pa_1007` αρώματα/ml (16). `pa_κατασκευαστής` = μάρκα (φίλτρο). `size`/`color` (ids 1–2)
  αχρησιμοποίητα. → Αποθηκεύουμε άξονες + την αντιστοίχιση σε `pa_*` για το push.
- One-shot import. **Πηγή κωδικών/barcodes/στοκ = export ειδών από το SoftOne** (εκεί ζουν
  τα barcodes του καταστήματος· στο Woo οι παραλλαγές δεν έχουν καν SKU)· **φωτογραφίες +
  σύνδεση = Woo** (`woo_variation_id`). Ταίριασμα SoftOne είδος ↔ Woo παραλλαγή με
  γονικό SKU + χρώμα + μέγεθος· ό,τι δεν ταιριάζει → λίστα για χειροκίνητη αντιστοίχιση.
  Όπου λείπει SKU/barcode παραλλαγής το παράγουμε (`ΓΟΝΙΚΟ-ΧΡΩΜΑ-ΜΕΓΕΘΟΣ`) και το
  στέλνουμε στο Woo. **Στοκ εκκίνησης: φυσική απογραφή** την ημέρα του cut-over.
  (Το HBOS `WmsVariationSyncService` κάνει ήδη το ίδιο parsing — καλό σημείο αναφοράς.)

**Φάση 4 — Push καταλόγου/στοκ/φωτογραφιών ekdosi → Woo.**
Απόλυτη ποσότητα (`stock_quantity = X`, ποτέ delta)· νυχτερινό diff → αναφορά.
Plugin `ekdosi-bridge` για WP (HMAC, κλείδωμα ekdosi-owned πεδίων, PDF στο «Ο λογαριασμός μου»).

**Φάση 5 — COD + επιστροφές.** Import αρχείου εκκαθάρισης courier (ACS/ΕΛΤΑ/BOX NOW)
→ μαζικές πληρωμές ταιριασμένες με αρ. παραγγελίας/voucher (`PaymentAllocator`)·
επιστροφές → πρόταση πιστωτικού 11.4. (Το HBOS ως πηγή αυτών = μελλοντική επιλογή.)

**Φάση 6 — Point of Sale** → §11.

**Σειρά:** Φάσεις 1–2 (e-shop, ο μεγαλύτερος πόνος) μπορούν να ξεκινήσουν αμέσως.
Το **κατάστημα φεύγει από το SoftOne μόνο όταν** είναι έτοιμα: Φάση 3 (barcodes) + POS
με **διασύνδεση καρτών** (§11.3) — δεν γίνεται cut-over καταστήματος με «μετρητά μόνο».

## 7. Γνωστές παγίδες

- **Διπλό ΑΛΠ** (voucher reissue, webhook retry, poll+webhook) → unique `(connection, order_id)`.
- **Διπλή έκδοση κατά τη μετάβαση:** όσο το παλιό πρόγραμμα κόβει ΛΙΑΣ, το ekdosi ΔΕΝ
  πρέπει να κόβει για τις ίδιες παραγγελίες → σαφής ημερομηνία cut-over (`invoice_min_date`).
- **Αρνητικά fees** → έκπτωση παραστατικού· **ΦΠΑ μηδέν στο Woo** → παράγεται από μικτό.
- **Παραλλαγές χωρίς SKU** — μόνο `variation_id` μέχρι τη Φάση 3.
- **HBOS roadmap (Inventory/WMS/ERP)** — αν ενεργοποιήσει δικό του στοκ, θα έχουμε δύο
  «πηγές» → τότε κουβέντα με τον dev (το HBOS να διαβάζει από ekdosi).
- **Διπλή έκδοση κατά τη μετάβαση από SoftOne** — ανά κανάλι (e-shop / κατάστημα)
  σαφής ημερομηνία από την οποία το SoftOne σταματά να κόβει τη συγκεκριμένη σειρά.

## 11. Point of Sale (Φάση 6)

### 11.1 Module + πρόσβαση
- **`companies.pos_enabled`** (default OFF) — ίδιο μοτίβο με `support_enabled` /
  `ergani_enabled` (`CompanyForm` toggle, `SupportCluster`-style κρυφό nav group
  «Ταμείο»). Η MyIP δεν το βλέπει καν.
- **Ρόλος `cashier`** («Ταμίας — μόνο POS»): default-deny εκτός των οθονών POS, ίδιο
  μοτίβο με `RestrictErganiStaff`/ρόλος `ergani`. Ο ταμίας είναι **συνδεδεμένος χρήστης**
  (χρειάζεται ταυτότητα για audit/ταμείο) — όχι ανώνυμο kiosk.
- **Θέσεις ταμείου (registers):** «Ταμείο 1» κ.λπ. — συσκευή + τερματικό καρτών (Viva
  terminal id) + αποθήκη/θέση στοκ + σειρά ΑΛΠ. Device pairing όπως `WorkCardKioskDevice`
  (μια φορά ανά συσκευή), μετά full-screen οθόνη (`WorkCardKiosk`-style σελίδα).

### 11.2 Η οθόνη πώλησης
- **Barcode:** οι USB/Bluetooth scanners είναι «πληκτρολόγιο» (HID) — πεδίο με μόνιμο
  focus, Enter = πρόσθεση γραμμής. Δεν χρειάζεται driver. Αναζήτηση και με όνομα/κωδικό
  → **πλέγμα χρώμα × μέγεθος** με διαθέσιμο στοκ.
- Καλάθι: ποσότητα, έκπτωση γραμμής/συνόλου, πελάτης **προαιρετικός** (λιανική χωρίς
  στοιχεία· με ΑΦΜ → ΤΠΥ με `AadeRegistryLookup`).
- **Πληρωμή:** Μετρητά (υπολογισμός ρέστων) · Κάρτα (§11.3) · IRIS (QR) · **μικτή**.
- **Έκδοση ΑΛΠ αμέσως μέσω παρόχου** → απόδειξη 80mm με το **QR του παρόχου**
  (υποχρεωτικό στη λιανική μέσω παρόχου). Εκτύπωση από τον browser σε θερμικό
  εκτυπωτή (Chrome `--kiosk-printing` = σιωπηλή εκτύπωση)· το συρτάρι ανοίγει από τον
  εκτυπωτή (ρύθμιση driver). Raw ESC/POS (QZ Tray) μόνο αν χρειαστεί.
- **Επιστροφή/αλλαγή:** σκανάρισμα QR/αριθμού απόδειξης → επιλογή γραμμών → πιστωτικό
  11.4 (`IssueCreditNote`) + επιστροφή χρημάτων (μετρητά ή **refund στην κάρτα από το
  ekdosi**) + προαιρετικά νέα πώληση (αλλαγή μεγέθους) — §10.6.
- **Ταμείο ημέρας:** άνοιγμα με ρέστα, εισπράξεις/αναλήψεις μετρητών, κλείσιμο με
  καταμέτρηση και αναφορά ανά τρόπο πληρωμής (εσωτερική — δεν είναι νόμιμο Ζ).
- Κάθε πώληση → `stock_movements` → push στο Woo (Φάση 4), ώστε το ίδιο νούμερο να μην
  πουληθεί δύο φορές.
- **Χωρίς internet δεν γίνεται πώληση με απόδειξη** (ο πάροχος θέλει real-time) →
  σύσταση: router με εφεδρικό 4G.

### 11.3 Διασύνδεση με το τερματικό καρτών (υποχρεωτική)
**Νόμος (Α.1155/2023 κ.ε.):** κάθε πληρωμή με κάρτα σε POS πρέπει να είναι συνδεδεμένη
με το παραστατικό. Στο myDATA (§5.2 v2.0.2) η γραμμή πληρωμής τύπου **7** φέρει
**υπογραφή πληρωμής** + `tid` (τερματικό) + `transactionId`:
- `ProvidersSignature` — όταν εκδίδεις **μέσω παρόχου** ← **ο δικός μας δρόμος**.
- `ECRToken` — όταν υπάρχει **ΦΗΜ (ταμειακή) + ERP**. Δεν μας αφορά (δεν θέλουμε ταμειακή).
- Σήμερα το ekdosi **δεν** παράγει καμία από τις δύο: το `MyDataConfigAudit` (POS-1)
  ήδη κοκκινίζει τύπο 7 σε χρήση, και ο InvoSign τον απορρίπτει («88-007»).

**Τι χρειάζεται τεχνικά:**
1. **Πάροχος που δίνει υπογραφή πληρωμής — ο InvoSign το ΥΠΟΣΤΗΡΙΖΕΙ** (επιβεβαιωμένο
   2026-10-02 από την τεκμηρίωσή του, «Ταυτόχρονη / Ετεροχρονισμένη συναλλαγή»,
   `invosign.gr/site/help_site/?page=pos_tautoxroni`). Το ekdosi έχει ήδη το κανάλι
   (`GrProviderSubmitter`, `InvoSignTransport`) — προστίθενται δύο κλήσεις:
   - **`iNVOSign_GetPayment.php`** (πριν την πληρωμή): `external_id`, `issueDate`, `branch`,
     `Type` (invoiceType), `series`, `aa`, `markid` (**κενό** = ταυτόχρονη, πριν το MARK·
     **το MARK** = ετεροχρονισμένη, για παραστατικό ήδη στο myDATA), `NetAmount`,
     `VatAmount`, `TotalAmount`, `Amount` (ποσό πληρωμής — επιτρέπει **μικτή** πληρωμή),
     `tipAmount`, **`TerminalID`** (το EFT-POS), `nsp` (σειρά cleartext υπογραφής:
     `0` = default, `1` = «Common WebECR»). Απάντηση: **`uid`** + **`paymentToken`
     {`timestamp`, `signature`, `amount`}** → αυτό στέλνεται στο τερματικό.
   - **Ταυτόχρονη:** μετά την έγκριση στο POS → κανονική **υποβολή παραστατικού** με
     `paymentMethodDetails` (τύπος 7 + υπογραφή + `tid` + `transactionId`).
   - **Ετεροχρονισμένη** (π.χ. εξόφληση ΑΛΠ αντικαταβολής/τιμολογίου αργότερα με κάρτα):
     2η κλήση **`iNVOSign_Payment.php`** {`uid`, `markid`, `signature`, `TerminalID`,
     `transactionId`} → `status`.
   - Ανοιχτό: πώς ακριβώς ταιριάζει το `uid` του InvoSign με το δικό μας document (ίδιος
     υπολογισμός uid ΑΑΔΕ από issuer/date/branch/type/series/aa) — sandbox test.
2. **Acquirer με cloud API τερματικού.** Η **Viva** (την έχει ήδη για το e-shop) δίνει
   4 πρωτόκολλα διασύνδεσης ERP↔POS ([έγγραφο Viva στην ΑΑΔΕ](https://aade.gr/sites/default/files/2024-10/Viva%20%CE%94%CE%B9%CE%B1%CF%83%CF%8D%CE%BD%CE%B4%CE%B5%CF%83%CE%B7%20ERP%20-%20POS%20v1.pdf)):
   **Cloud Terminal API** (το σωστό για εμάς: ekdosi cloud → Viva cloud → τερματικό,
   χωρίς τίποτα τοπικό), Local Terminal API (ίδιο LAN), App-to-App (Android/SoftPOS στην
   ίδια συσκευή), TCP/IP (Prolin). Συμβατά τερματικά: Paydroid (A920/A80/A35/A77/A50),
   Sunmi/Ciontek, και **SoftPOS** (το viva.com Terminal app σε κινητό/tablet).
   **Μετά την 1η συνδεδεμένη συναλλαγή κλειδώνει το πληκτρολόγιο του τερματικού**:
   πώληση, ακύρωση, επιστροφή, δόσεις ξεκινούν **μόνο** από το ERP (ekdosi).
3. **Ροή** (InvoSign πλευρά επιβεβαιωμένη· τερματικό πλευρά → έρευνα §11.6):
   καλάθι → δέσμευση ΑΑ + ποσά → `GetPayment` (InvoSign) → `paymentToken` → `sale` στο
   τερματικό (ποσό + token/υπογραφή + uid) → ο πελάτης ακουμπά την κάρτα → **webhook**
   Viva (`transactionId`, `tid`) → έκδοση ΑΛΠ μέσω παρόχου με `paymentMethodDetails`
   (τύπος 7 + υπογραφή + tid + transactionId) → απόδειξη. Αποτυχία/ακύρωση πληρωμής →
   δεν εκδίδεται ΑΛΠ (ή ακυρώνεται το πρόχειρο).
4. Χτίζεται πάνω στο υπάρχον seam: `PaymentGateway` (+ `WebhookGateway`) /
   `PaymentGatewayRegistry` ως **`terminal`** capability (`docs/payment-connectors.md`,
   `docs/payment-gateways-design.md`) — νέος `VivaTerminalGateway`, idempotent στο
   `transactionId`.
5. Άλλος acquirer (Cardlink/Worldline/Nexi/Τράπεζα) = νέος adapter στο ίδιο contract·
   **πρώτα Viva**, γιατί υπάρχει ήδη λογαριασμός και καθαρό cloud API.

### 11.4 Hardware (ενδεικτικά)
Tablet/PC με Chrome · USB/Bluetooth barcode scanner · θερμικός εκτυπωτής 80mm
(+ συρτάρι στο RJ11 του) · τερματικό Viva (Paydroid ή SoftPOS) · προαιρετικά
εκτυπωτής ετικετών barcode για είδη χωρίς barcode.

### 11.5 MVP καταστήματος
Πώληση με barcode + μετρητά/κάρτα Viva (συνδεδεμένη) + ΑΛΠ μέσω παρόχου + απόδειξη 80mm
+ επιστροφή/αλλαγή + κλείσιμο ημέρας + στοκ → Woo. Εκτός MVP: IRIS QR, δόσεις, πολλαπλά
καταστήματα, προσφορές/κουπόνια ταμείου, offline.

### 11.6 Σύνδεση με το ΤΟΠΙΚΟ τερματικό — έρευνα σε εξέλιξη
Ανοιχτό: πώς ένα cloud app στέλνει `sale` (ποσό + `paymentToken`) σε τερματικό στο
κατάστημα και παίρνει πίσω `transactionId`/`tid` — ανά acquirer (Viva / Cardlink /
Worldline / Nexi / Epay): cloud API, τοπικό ECR πρωτόκολλο μέσω μικρού bridge agent στο
PC του καταστήματος, ή Android app-to-app. Το `nsp=1` «Common WebECR» του InvoSign δείχνει
ότι υπάρχει κοινό spec για web ECR — να βρεθεί ποιος το εκδίδει.
